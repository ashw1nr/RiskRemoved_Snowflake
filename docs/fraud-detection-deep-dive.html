Example — Why CTR matters: A customer deposits Rs 12,00,000 in cash at a branch counter. Because 12L ≥ 10L (the CTR_CASH_THRESHOLD clause), the bank must file a CTR — no suspicion needed. But if the same customer deposits Rs 9,50,000 instead? No CTR is required. A money launderer exploits this gap by structuring — splitting Rs 20L into three deposits of Rs 9.5L, Rs 9.2L, Rs 9.8L across different accounts. Each is below 10L, so no automatic CTR. The STRUCTURING_CROSS_ACCOUNT rule exists to catch exactly this pattern.

When the structuring rule fires, this txn_id appears in the signal's evidence_txn_ids array. Step 1: Threshold Resolution

The rule SQL does a CROSS JOIN to V_POLICY_CLAUSE_CURRENT, pivoting four clause IDs:

SELECT
  MAX(IFF(clause_id='CTR_CASH_THRESHOLD',    threshold_lower, NULL)) AS ctr_threshold,  -- 1000000
  MAX(IFF(clause_id='STRUCTURING_BAND',       threshold_lower, NULL)) AS band_lower,     -- 0.90
  MAX(IFF(clause_id='STRUCTURING_BAND',       threshold_upper, NULL)) AS band_upper,     -- 0.999
  MAX(IFF(clause_id='STRUCTURING_MIN_ACCOUNTS',threshold_lower,NULL)) AS min_accounts,   -- 2
  MAX(IFF(clause_id='STRUCTURING_WINDOW_DAYS', threshold_lower, NULL)) AS window_days    -- 30
FROM V_POLICY_CLAUSE_CURRENT

Step 2: Transaction Filtering

From DT_TRANSACTIONS_ENRICHED, select only:

  • leg_side = 'C' — credit legs (deposits) only
  • is_cash = TRUE — cash channel per REF_CHANNEL
  • NOT is_internal_account — exclude bank's own cash desk
  • amount_inr BETWEEN 0.90 * 10L AND 0.999 * 10L = Rs 9,00,000 to Rs 9,99,000

Step 3: Tumbling Window

FLOOR(DATEDIFF('day', '1970-01-01', txn_date) / 30) AS bucket
-- Example: 2022-09-01 → bucket 641 (window: 2022-08-26 to 2022-09-24)

Step 4: Aggregation & Firing

GROUP BY party_id, bucket
HAVING COUNT(DISTINCT account_id) >= 2  -- threshold from STRUCTURING_MIN_ACCOUNTS

-- This is the CREATE OR ALTER DYNAMIC TABLE statement.
-- Snowflake runs this SELECT on every refresh (incrementally).

SELECT
    t.txn_id,
    t.txn_pair_id,
    t.leg_side,                                    -- 'C' or 'D'
    t.account_id,
    t.counterparty_account_id,
    t.txn_timestamp,
    TO_DATE(t.txn_timestamp)              AS txn_date,       -- derived for window bucketing
    t.amount,
    t.currency,
    t.amount_inr,                                  -- THE detection column
    t.txn_type,
    t.channel,
    ch.is_cash,                                    -- ← FROM REF_CHANNEL (is this a cash channel?)
    ch.is_instant,                                 -- ← FROM REF_CHANNEL
    t.source_ref,
    a.party_id,                                    -- ← FROM ID_MAP_ACCOUNT (who owns this account?)
    a.src_bank_id = 'BANK_INTERNAL'    AS is_internal_account,   -- is this the bank's own cash desk?
    cp.party_id                        AS counterparty_party_id, -- ← FROM ID_MAP_ACCOUNT (counterparty)
    cp.src_bank_id = 'BANK_INTERNAL'   AS is_internal_counterparty,
    p.branch_region,                               -- ← FROM DT_DIM_PARTY (for Row Access Policy)
    p.branch_code,                                 -- ← FROM DT_DIM_PARTY
    p.party_type,                                  -- ← FROM DT_DIM_PARTY
    ra.account_type,                               -- ← FROM RAW_ACCOUNTS (SAVINGS/CURRENT/FD)
    t.ingested_at

The Actual SQL — STRUCTURING_CROSS_ACCOUNT Rule

This is the complete query that executes inside the dynamic table. Every number comes from V_POLICY_CLAUSE_CURRENT, never a hardcoded value.

-- STEP 1: Resolve thresholds (CROSS JOIN — one row from the policy view)
WITH thresholds AS (
    SELECT
        MAX(IFF(clause_id='CTR_CASH_THRESHOLD',     threshold_lower, NULL)) AS ctr_threshold,   -- 1000000
        MAX(IFF(clause_id='STRUCTURING_BAND',        threshold_lower, NULL)) AS band_lower,      -- 0.90
        MAX(IFF(clause_id='STRUCTURING_BAND',        threshold_upper, NULL)) AS band_upper,      -- 0.999
        MAX(IFF(clause_id='STRUCTURING_MIN_ACCOUNTS', threshold_lower, NULL)) AS min_accounts,   -- 2
        MAX(IFF(clause_id='STRUCTURING_WINDOW_DAYS',  threshold_lower, NULL)) AS window_days     -- 30
    FROM GOVERNANCE.V_POLICY_CLAUSE_CURRENT
),

-- STEP 2: Filter qualifying deposits
qualifying_deposits AS (
    SELECT
        e.party_id,
        e.account_id,
        e.txn_id,
        e.txn_timestamp,
        e.amount_inr,
        FLOOR(DATEDIFF('day', '1970-01-01', e.txn_date) / c.window_days) AS bucket,
        c.ctr_threshold, c.band_lower, c.band_upper, c.min_accounts, c.window_days
    FROM CURATED.DT_TRANSACTIONS_ENRICHED e
    CROSS JOIN thresholds c
    WHERE e.leg_side = 'C'                          -- credit legs only (deposits)
      AND e.is_cash                                 -- cash channel only
      AND NOT e.is_internal_account                 -- exclude the bank's cash desk
      AND e.amount_inr BETWEEN c.band_lower * c.ctr_threshold
                            AND c.band_upper * c.ctr_threshold
                                                    -- Rs 9,00,000 to Rs 9,99,000
)

-- STEP 3: Aggregate and fire
SELECT
    'STRUCTURING_CROSS_ACCOUNT'                                       AS rule_id,
    d.party_id,
    NULL::VARCHAR                                                     AS account_id,
    TO_VARCHAR(DATEADD('day', (d.bucket * d.window_days)::INT, '1970-01-01')) AS window_bucket,
    COUNT(DISTINCT d.account_id)::NUMBER(20,4)                        AS metric_value,
    d.min_accounts::NUMBER(20,4)                                      AS threshold_value,
    ARRAY_AGG(d.txn_id) WITHIN GROUP (ORDER BY d.txn_id)              AS evidence_txn_ids,
    OBJECT_CONSTRUCT(
        'deposit_count', COUNT(*),
        'deposit_total_inr', SUM(d.amount_inr),
        'accounts', ARRAY_AGG(DISTINCT d.account_id),
        'band_lower_inr', d.band_lower * d.ctr_threshold,
        'band_upper_inr', d.band_upper * d.ctr_threshold,
        'ctr_threshold_inr', d.ctr_threshold,
        'window_days', d.window_days
    )                                                                 AS detail,
    MAX(d.txn_timestamp)                                              AS last_txn_at,
    'STRUCTURING_CROSS_ACCOUNT' || '|' || UPPER(d.party_id) || '|'
        || TO_VARCHAR(DATEADD('day', (d.bucket * d.window_days)::INT, '1970-01-01'))
                                                                      AS signal_business_key
FROM qualifying_deposits d
GROUP BY d.party_id, d.bucket, d.window_days, d.min_accounts, d.ctr_threshold, d.band_lower, d.band_upper
HAVING COUNT(DISTINCT d.account_id) >= d.min_accounts   -- ← THE FIRING CONDITION

ROUTE_SIGNALS — The 5-Step MERGE

Execution: SERIAL — triggered by SYSTEM$STREAM_HAS_DATA, runs as a single atomic transaction
Reads from: SIGNALS_STREAM + RULE_DEFINITION + SIGNAL + CASE_RECORD + DT_DIM_PARTY
Writes to: SIGNAL + CASE_RECORD + CASE_SIGNAL (all within one COMMIT)

The 5 SQL Statements Inside the Transaction

Statement 1: MERGE into SIGNAL

MERGE INTO EVIDENCE_CHAIN.SIGNAL t
USING (
    SELECT
        'SIG-' || LEFT(SHA2(b.signal_business_key, 256), 16) AS signal_id,
        b.signal_business_key,
        b.rule_id,
        r.rule_version,        -- ← from RULE_DEFINITION
        b.party_id,
        b.account_id,
        r.severity,            -- ← from RULE_DEFINITION (not from the signal itself)
        b.window_bucket,
        b.last_txn_at AS fired_at,
        b.metric_value,
        b.threshold_value,
        b.evidence_txn_ids,
        b.detail
    FROM SIGNALS_STREAM b
    JOIN RULE_DEFINITION r ON r.rule_id = b.rule_id   -- look up severity + version
) s
ON t.signal_business_key = s.signal_business_key      -- THE IDEMPOTENT KEY
WHEN MATCHED AND (evidence changed) THEN UPDATE SET ...
WHEN NOT MATCHED THEN INSERT (...) VALUES (...);
Output — New row in SIGNAL table:

Statement 2: INSERT into CASE_RECORD (if no open case for this party)

INSERT INTO EVIDENCE_CHAIN.CASE_RECORD (case_id, party_id, case_type, branch_region, opened_at)
SELECT
    'CASE-' || LEFT(SHA2(c.party_id || '|' || MIN(c.signal_business_key), 256), 16),
    c.party_id,
    'AML',                                -- case_type from routing.case_type_by_rule
    p.branch_region,                      -- ← from DT_DIM_PARTY (NOT NULL constraint)
    CURRENT_TIMESTAMP()
FROM (signals owed a case) c
LEFT JOIN DT_DIM_PARTY p ON p.party_id = c.party_id
WHERE NOT EXISTS (
    SELECT 1 FROM CASE_RECORD o
    WHERE o.party_id = c.party_id
    AND o.status IN ('OPEN', 'INVESTIGATING', 'DRAFTED')  -- open_case_statuses
)
GROUP BY c.party_id, p.branch_region;
Output — New row in CASE_RECORD: 
| case_id              | party_id   | case_type | status | branch_region | opened_at           |
|----------------------|------------|-----------|--------|---------------|---------------------|

Statement 3: INSERT into CASE_SIGNAL (attach signal to case)

INSERT INTO EVIDENCE_CHAIN.CASE_SIGNAL (case_id, signal_id, attached_at)
SELECT o.case_id, c.signal_id, CURRENT_TIMESTAMP()
FROM (signals owed a case) c
JOIN (earliest open case per party) o ON o.party_id = c.party_id;
Output — New row in CASE_SIGNAL:

|----------------------|--------------------|---------------------|
| CASE-4399c4c86db5c6ea| SIG-4399c4c86db5   | 2026-09-29 10:06:15 |

Statement 4: UPDATE case_type to CROSS_DOMAIN (if 2+ rule families)

-- Only fires if COUNT(DISTINCT rule_id) >= 2 across attached signals
UPDATE CASE_RECORD c SET case_type = 'CROSS_DOMAIN'
WHERE ... AND c.case_type IS DISTINCT FROM 'CROSS_DOMAIN';
-- In our example: only 1 rule → stays AML, this UPDATE affects 0 rows.

Statement 5: COMMIT

COMMIT;
-- Returns: {"signals_inserted":1, "signals_updated":0, "cases_opened":1, "signals_attached":1, "cases_escalated":0}
Atomicity guarantee: If Statement 3 fails (e.g., a signal can't be attached), the entire transaction rolls back. SIGNAL and CASE_RECORD inserts are undone. The stream is unconsumed. The next task run sees the same changes and retries.
